## Survivorship (numeric)

## PIT fundamentals

`FUND_pit = FUND_true.shift(5)`. Aligning on `FUND_true` as if it were knowable that day leaks unpublished prints.

### Crypto PIT audit note (pointer)

Before mining crypto “alpha,” audit **availability time**, not just file existence ([arXiv:2608.25348](https://arxiv.org/abs/2608.25348) on Binance BTCUSDT USD-M perps). Teaching checklist: **no same-bar execution**; **funding lag** (do not shift realized funding backward); **no backfill** to manufacture continuity; if **OI publication time is unverified**, disable OI as an alpha input. Full foil + lab in `frontier-tsfm-altdata-crypto`.

## Why `panel_nav_honest_shift1` equals `signal × next_ret`

Those two NAV prints are equal because they are the **same PnL products shifted by one timestamp**: `shift(1)×ret` vs `signal×ret.shift(-1)`. Equal NAV is **not** a look-ahead test — both already use next-period returns with a prior signal. Same-bar `signal×ret` would be look-ahead. (See lab print `equality_why`.)

## Information bars vs time bars (AFML ch.2)

**Intuition:** A **time bar** samples the wall clock (every minute, every day). Markets do not speak at a constant rate: a quiet hour and a news burst both become “one bar,” so return variance and microstructure noise look uneven. **Tick / volume / dollar bars** sample *activity* instead — emit a bar after \(N\) trades, \(V\) shares, or \(D\) dollars of notional. Busy periods mint more bars; quiet periods fewer. That is a **research sampling** choice for cleaner statistical clocks — **not** an HFT latency or execution recipe.

**Toy comparison** on one synthetic 5,000-tick tape (`examples/p2/01_data_cleaning.py`):

| Clock | n_bars | mean \|ret\| | std(ret) |
|-------|--------|-------------|----------|
| time/tick every 50 | 100 | ≈0.0045 | ≈0.0058 |
| volume 200 shares | 241 | ≈0.0030 | ≈0.0036 |
| dollar ≈200×mid | 231 | ≈0.0030 | ≈0.0038 |

Activity clocks produce **more** bars with **smaller** per-bar moves on the same tape — the series is closer to an “information clock.”



## Mask-first / upstream contamination (A-share comparison case: limit closes in rolling windows; US analogue: halted / LULD-paused / no-quote rows)

[arXiv:2507.07107](https://arxiv.org/abs/2507.07107) documents a costly A-share pipeline failure: **limit-up/down closes are non-executable**, yet they enter rolling means / correlations / ranks **before** any row filter — **upstream contamination**.

**Paper ablation (warning numbers only — not course alpha):** removing the mask **inflates apparent IC by ~+18%** while **cutting realised Sharpe by ~0.44** — the model learns returns it cannot trade.

**Boolean mask-first contract (what this lesson keeps):**

1. Build `M[t,i]` at load time (tradable: not halted ∧ not at limit ∧ past seasoning).
2. Every rolling operator reads **only** cells with `M=1`; any `M=0` in the window → mark output unreliable (conservative).
3. **Post-hoc row drops cannot un-poison** aggregates already computed.

### Five-close sketch (lab printout)

| day | close | tradable? | naive MA3 | mask-first MA3 |
|-----|-------|-----------|-----------|----------------|
| 0 | 10.0 | 1 | — | — |
| 1 | 10.1 | 1 | — | — |
| 2 | 10.2 | 1 | 10.10 | 10.10 |
| 3 | **11.2** (limit print) | **0** | **10.50** | **10.15** |
| 4 | 10.3 | 1 | **10.57** | **10.25** |

The limit print contaminates the naive MA until it rolls off; mask-first **never reads it**.

## Data versions, corporate actions & trading calendars

**Intuition:** the same stock over the same period can show a different monthly return under a different “data version” or calculation convention. A backtest number is reproducible only if you write down **which version you used**.

**Real example (verified on Ken French’s official site):** the [Ken French Data Library](https://mba.tuck.dartmouth.edu/pages/faculty/ken.french/data_library.html) states that CRSP’s Legacy (FIZ) files were discontinued after the December 2024 data release; **beginning with the January 2025 data release**, US research returns are generated from the new Flat File Format 2.0 (CIZ). The site highlights: FIZ monthly returns are “month to month holding period returns with dividends reinvested at month-end”; CIZ monthly returns are “**compounded daily returns** with dividends reinvested on their **ex-dates**.” The site also keeps historical data based on the legacy FIZ format.

**Formula:** with daily total return `r_d = (P_d + D_d) / P_(d−1) − 1` (`D_d` non-zero only on the ex-date), the CIZ-style monthly return is `R_m = Π_(d in m) (1 + r_d) − 1`; the month-end-reinvest style is roughly `(P_end + D) / P_start − 1`.

**Numeric example (`examples/p2/05_data_versions_calendar.py`, seed=7, synthetic):** the same prices and one dividend of 2.0:

```text
Jan month-end reinvest  : -0.102533
Jan ex-date reinvest    : -0.104362
difference (bp)         : -18.28
```

The two conventions differ by about 18 bp — the data are not wrong; the **convention differs**.

**Corporate action (split):** on a 2-for-1 split day the raw price goes from 51.0 to 25.6, producing a fake −49.8% “crash”; the adjusted return that day is only +0.39%:

```text
raw daily ret     : [0.02, -0.498, 0.0117]
adjusted daily ret: [0.02, 0.0039, 0.0117]
```

**Trading calendar:** two markets have different holidays (market B is closed on 04-04). Forward-filling B’s **returns** (ffill) “invents” a return on a closed day; align by each market’s own calendar, or use only the intersection of open days:

```text
A days=8 B days=7 inner-join days=7
ffill rows where B return is a stale copy: 1
```

**Practical rule:** the data sheet states: source + version/release month + return convention (when dividends are reinvested) + adjustment method + trading calendar used. After a version change, rerun the old result first, then compare.

## Raw vs adjusted prices and total return; delisting

**Raw prices (per review item R21):** raw (unadjusted) prices are used for the historical nominal price scale and the share/cash ledger; whether a strategy could trade at a given price and size still depends on the session, quotes, trading status, liquidity and the order/fill model at that time — raw OHLC or the last trade price is not automatically executable. Split-adjusted and total-return series each record their adjustment scope; never count the same dividend twice, and a split adjusts the share count too rather than creating wealth out of nothing.

Note: the Massive stocks-page example labels `adjusted:true` as **split-adjusted** — do not assume it includes dividends.

`examples/p2/05_data_versions_calendar.py` new section D (earlier numbers unchanged):

```text
ledger wealth [6000, 6100, 6080, 6120, 6160]
split-adjusted price returns [0.0167, -0.0033, -0.0099, 0.0066]; total returns [0.0167, -0.0033, 0.0066, 0.0066]
double-counted dividend gives 0.0230 vs correct 0.0066; delisting: missing return flagged, not dropped or set to 0
```

**ALFRED revision as-of:** align with `merge_asof` on **release time** (not observation date); a series with no release time cannot enter the features.

## Common mistakes / pitfalls

1. Backtesting a decade with today’s members only.  
2. Fundamentals without PIT.  
2b. Crypto archives that look complete but fail availability-time audits (same-bar / funding lag / backfill / unverified OI).  
3. UTC vs local off-by-one.  
4. Mixing raw/adj silently.  
5. No hash / no version.
6. Treating info bars as an HFT execution recipe rather than a research sampling clock.
7. Comparing clocks on different underlying tapes without saying so.
8. Switching data versions (e.g. FIZ→CIZ) without recording it, mistaking a convention change for a strategy change; ffilling **returns** across closed days; computing split-day returns on raw prices.
9. Treating the raw close as an executable price; treating a FRED series’ public-domain label as permission for the FRED service, caching or model training; calling yfinance official data.
